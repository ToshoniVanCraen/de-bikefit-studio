# CMS writer freeze — staging-only candidate (29 October 2026)

This is a database guard, not release authorisation. It has **not** run on Neon Staging or Production. The generator only writes reviewable SQL to a new mode-0600 file; it never connects. Arend owns independent Staging rehearsal and deployment. No Production query, write, credential change or deployment is authorised here.

## Role and coverage contract

Four distinct roles are required: `APP` is the **existing deployed** `DATABASE_URL` login and current owner of every `cms_*` ordinary table; its credential remains unchanged. `CLI` is a new LOGIN used **only** in the one-off correction CLI `DATABASE_URL`, never in Vercel. `OWNER` is a dedicated NOLOGIN guard/table owner. `INSTALLER` is a privileged operator login, never used by the app/CLI, and must be a member of APP (to transfer initial table ownership) and OWNER (to manage the guard). APP and CLI must have no superuser, CREATEROLE, BYPASSRLS or guard/installer membership. The install and every verification reject any other LOGIN that can administer roles directly or via `SET ROLE`, or assume OWNER/INSTALLER. They also reject any LOGIN that can create relations directly or by `SET ROLE` into a CREATE-capable role, even when that privilege is not inherited, or that owns the database or a CMS-capable schema and could self-grant CREATE. CLI must be fresh, with no pre-existing CMS grants. Existing old deployment URLs using APP are guarded automatically; no app credential rotation is required **if APP can be safely demoted and its schema/database DDL privileges removed**. If APP owns the database/schema or holds irreducible CREATEROLE/CREATE privileges, this four-role plan cannot safely guard future `cms_*` tables; hold, then review a separate app-role migration. The SQL must not silently modify the webshop's schema ownership or credentials. The installer preflight additionally requires database CREATE, effective inherited owner privileges and `CREATE WITH GRANT OPTION` on each CMS schema to make the temporary, transaction-local ownership-transfer grants. The local PGlite integration uses the `postgres` superuser as installer; it **does not prove** a non-superuser Neon INSTALLER can transfer ownership or grant CREATE. Arend must prove those exact operations on a disposable Staging branch before any live Staging installation, and hold if Neon disallows them.

**Current Staging blocker (Arend read-only audit, 29 Oct):** its single `neondb_owner` role owns all 33 `cms_*` tables and has CREATEROLE. It does **not** satisfy the APP preflight. This candidate must not be installed on that branch until Arend demonstrates a distinct privileged INSTALLER and safe demotion/removal of APP's database/schema CREATE and role-admin powers, while old deployment URLs remain guarded. If Neon cannot support that, hold and design a separate app credential migration; do not weaken the checks. The remaining Neon branch slot is suitable for a disposable Production-shaped rehearsal only if Arend arranges it; preserve the existing recovery snapshot.

Every current ordinary `cms_*` table across non-system schemas gets `BEFORE INSERT OR UPDATE OR DELETE` and `BEFORE TRUNCATE` **statement-level** `ENABLE ALWAYS` triggers, including empty UPDATE/DELETE, booking, Beheer, rate-limit, session, audit and email tables. Non-ordinary CMS relations, CMS-owned/default `nextval` sequences, and any pre-existing non-internal CMS trigger require redesign and fail preflight. Existing triggers could run before the guard alphabetically and cause external effects; verification rejects new user triggers as drift. CLI is intentionally granted SELECT/INSERT/UPDATE/DELETE, not TRUNCATE or sequence privileges, because the correction patch needs no TRUNCATE and checked-in CMS migrations use no sequences. A SECURITY DEFINER function owned by OWNER, with a fixed `pg_catalog` search path, checks a protected singleton state. While enabled, only exact `session_user = CLI` can write. Missing/corrupt state and SQL errors abort the write. APP/CLI cannot alter guard state or disable triggers after ownership transfer. Verification checks all discovered `cms_*` relations against the manifest, trigger identities/types/modes and role safety. A new table or DDL drift makes verification fail; migration/DDL ingress must be suspended separately. Trigger coverage is **not** an automatic DDL event trigger. Role and schema CREATE checks are a prerequisite, not a claim of live Neon proof.

INSTALL, FREEZE, UNFREEZE and UNINSTALL each run in one transaction. INSTALL takes table DDL locks, waits for in-flight writes and commits the enabled guard with complete coverage or rolls back. UNFREEZE atomically changes the state; old app URLs resume normal writes only after commit. UNINSTALL drops triggers and restores original APP ownership, revokes CLI grants added for this fresh role, and removes the guard in one transaction. Other pre-existing table grants remain. Neither installation nor uninstall targets webshop tables. The SQL does not change existing webshop ACLs; their ordinary behavior must be separately proven. There are no CMS sequences in checked-in migrations; installation refuses `cms_*` sequence relations, dependencies and `nextval` defaults. `nextval`/`setval` are not trigger-protected. Arend must confirm live catalog and default privileges before any role change.

## Failure rule

A failed INSTALL rolls back. Missing/disabled trigger, unexpected CMS relation, role/owner/DDL drift or failed drain means **hold**, keep ingress paused and do not run the correction CLI. Neon HTTP correction writes are independently committed; a failed apply may be partial. Keep the first backup and snapshot. For a controlled restore, verify/re-establish the freeze, use the exact CLI role and first backup, audit, then atomically unfreeze. Dropping triggers while frozen is not rollback; unfreeze leaves the guard installed but permissive.
